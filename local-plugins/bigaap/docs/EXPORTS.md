# Exports

Export is the moment an artifact loses its context.

Inside a run directory, a prompt sits beside the coverage report that qualifies it, the
blocked-prompt that may contradict it, and the history that dates it. Copied into a
product repository it has none of that, and it reads as a specification.

The goal is not to make export difficult. It is to make it impossible for an exported
file to be read as more certain than the evidence behind it.

## Two refusals with no override

**Stale implementation prompts.** The values in the file are no longer what the analysis
concluded. Exporting one hands somebody instructions to build the wrong thing, and
nothing at the destination can detect it.

**Blocked implementation prompts.** The safety gate already refused to stand behind these
instructions. Exporting them routes around the gate, which is the one thing the gate
exists to prevent.

Neither has a force flag. A stale prompt is fixed by regenerating it and reading what
changed; a blocked one is fixed by changing what the gate objected to.

## What a stale *report* does

It exports, with the staleness recorded in its header.

The asymmetry is deliberate and it is not a compromise. A coverage report describing an
earlier capture is **still a true account of that capture**. A build instruction
describing an earlier capture is **not still a true instruction**. One remains accurate
about the past; the other becomes wrong about the present.

## What every export carries

```
artifactKind · mode · sourceKind · source · irHash · generatedAt
generatorVersion · status · freshnessAtExport · limitations · regenerateWith
```

Plus a rendered banner for whoever opens the file at the destination — who has no run
directory, and probably no idea this tool exists:

```
> **Exported artifact.** Generated by bigaap `0.1.0` on 2026-01-01T00:00:00.000Z
> from `https://example.test/` in `recreate` mode.
>
> This file was separated from the analysis that produced it. Its limitations:
> - No tolerance in this system is validated. Acceptance criteria are stated
>   targets, not certified thresholds.
```

Two limitations are attached automatically because they are the two most likely to be
lost in transit:

- **Screenshot evidence.** Every value in the file is estimated. Nothing about being
  copied makes it a measurement.
- **Unvalidated tolerances.** Acceptance criteria are stated targets. No threshold in
  this system has been certified.

## Batch exports report every answer

Exporting a spec, a token file and a prompt where one is refused returns the two that are
safe **plus** a clear account of the third — not nothing, and not a silent partial. The
plan carries:

- `allowed` — with each file's export header
- `refused` — with the code, the message and the remedy for each
- `warnings` — stale reports and unverifiable files that were exported anyway
- `complete` — false when anything was refused, so a caller cannot describe a partial
  export as a complete one
- `refusalsAreFinal` — true when a refusal cannot be resolved by regenerating

## Refusal codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `stale-implementation-prompt` | Its source moved | Regenerate, read what changed, export |
| `blocked-implementation-prompt` | The safety gate refused the run | Read `output/blocked-prompt.md` |
| `incompatible-artifact` | Produced under a different tool version | Re-capture with the current tool |
| `export-without-metadata` | No readable metadata block | Regenerate |
| `unknown-artifact` | Not a registered artifact | Nothing can say whether exporting it is safe |

## Why metadata is mandatory for export

An artifact with no metadata cannot be exported at all, even a harmless-looking report.

Inside a run directory a file's path explains it. Once exported, the metadata block is
the **only** thing left that can — which is exactly why it travels inside the file rather
than beside it. See [ARTIFACTS.md](ARTIFACTS.md) for the fields and
[FRESHNESS.md](FRESHNESS.md) for how they are checked.
